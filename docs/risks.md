## R-021：协议包 id 的推导方法可能整体偏移

**概率**：已发生　**影响**：高（任何 play 阶段包都可能发错 id，表现为被服务端静默断开）

**现状**：play 阶段的包 id 由分析产物中"注册链内的出现序号"推导。该方法曾漏掉同链里的通用包
（`CommonPacketTypes`），导致 `KeepAlive`、`MovePlayerPos`、`Pong` 各偏移 1。修正后移动包仍被服务端拒绝，
说明还可能存在其他偏差（例如客户端收到的高频 10 字节包实际 id 与表中 `KeepAlive = 45` 不符）。

**缓解**：
- 每个用到的 id 都必须在真实服务端上验证"收得到 / 发得出"，不能只靠计数；
- 保留 `walk` 命令作为验证手段：它能在不渲染的情况下把移动包真实性暴露出来；
- 优先用官方客户端抓包（用户已准备带 MCP 的 Fabric 客户端）得到权威 id，再回填本表。

**2026-10-29 更新**：已用"逐 id 探针 + 服务端解码报错点名"的方法得到服务端 27–45 的权威映射
（见 `docs/specs/network/play-movement.md` §6.1），并据此修正了 `keep_alive = 28`、`move_player_pos_rot = 31`、
`pong = 45` 等。方法本身成立：**服务端的报错信息就是可用的 id 字典**。
剩余偏差（分析 jar 与服务端差一个注册项）已定位，不再属于未知。

**复查条件**：官方客户端抓包结果与本地服务端实测一致后关闭。

## R-022：客户端移动速度约为原版的一半

**概率**：已发生　**影响**：中（协议正确，手感与位移速率不符原版；影响等效性验收）

**证据**：同一服务端、同一输入条件下，官方客户端 4.258 格/秒，我们的客户端 2.201 格/秒；
10 秒内收到 23 次服务端位置修正，说明服务端反复把我们拉回。

**假设**：客户端仿真节拍与服务端 20 TPS 不一致（本地 tick 实际快于 20 Hz，位置包间隔不均匀），
服务端按自己的物理重算后判定偏差并回拉，净位移被抵消。

**缓解**：
- 客户端 tick 改为严格 20 Hz 的单调时钟列队，位置包与 `client_tick_end` 成对、每 tick 恰好一次；
- 在平地上重新测量，并同时记录 `onGround` 与每次修正的偏差；
- 若修正归零而速度仍偏低，再检查 `moveRelative` 的速度换算与摩擦取值。

**2026-10-29 更新（部分收敛）**：定位到测量方法问题后重测，配对结果为官方 4.291 格/秒、
我们 4.479 格/秒，差异 **+4.4%**（此前 2.201 的读数是 23 次回拉污染了单次采样）。
tick 速率实测 19.4–19.8/s，原因是 Windows `Task.Delay` 的 ~15.6 ms 调度粒度。
**剩余**：修正次数仍偏多（12 秒 24 次），说明 tick 略快于服务端或每 tick 位移略有偏差。

**下一步**：用 `Stopwatch` 计时 + 高精度等待把 tick 锁到 20.00/s（必要时混合自旋），再配对重测。

**2026-10-29 关闭**：配对实测（同服同账号、平地、按真实时间差计算）官方 4.307 格/秒、
我们 4.317 格/秒，差异 **0.2%**；修正 2 次/15 秒。逐 tick 精度由 `WalkingSpeedPrecisionTests` 直接钉住
（0.2159 格/tick），斜向同速由 `DiagonalWalkingIsNotFasterThanStraightWalking` 钉住。

**过程中的一次测量错误**：初版脚本按"采样点数"而非实际经过时间相除，报出 +3.8%；已更正。
教训记录在 §7.13。

**复查条件**：与官方客户端的位移速率差异 ≤ 5% 且修正次数接近 0 后关闭。**（已满足）**

## R-023：每 tick 的碰撞求解与原生不完全一致，导致服务端频繁回拉

**概率**：已发生　**影响**：中（速度已对齐到 ±3%，但服务端每秒约回拉两次，长距离行走会出现顿挫）

**证据**：tick 速率与位移速度对齐后，同样的行走仍触发约 25 次/12 秒的服务端位置修正。

**原因**：服务端会在 `handlePlayerPositionChange` 里用自己的 `move()` 重算一次，残差 > 0.25 格即回拉。
我们的 `Entity.Move` 是独立实现（逐轴 Y→X→Z、0.5 格步长、贴面钳制），在台阶、方块边缘、斜面等
几何情形下无法与原生求解逐位相同。

**2026-10-29 精确定位**：原版的回拉判定是"目标位置是否引入新碰撞体"，与残差大小无关
（残差 >1/16 格只记 WARN）。我们侧的日志里从无 `moved wrongly`，说明 `fail = false`，
所以每次回拉都来自 `isEntityCollidingWithAnythingNew` 为真——**即我们申报的目标位置让包围盒与
新方块重叠**，最可能是离地贴面钳制留了微小穿透。

**缓解（已收窄）**：记录每次修正前后的「目标位置 / 旧包围盒 / 新重叠方块」，确认是否恒为脚下方块；
若是则修 `Entity.Move` 的贴面钳制，而不是改速度或节拍。

**2026-10-29 已修复（最终方案）**：根因是客户端世界**没有持续加载区块**——只收了出生点附近的 9 个，
走出去以后按空气处理，于是走进服务端有实地的区域。中间曾尝试"未加载即不可通行"，但那是原版没有的
隐形墙（所有者指出并纠正）。最终按原版语义实现流式加载：`client_information` 声明视距、
`chunk_batch_received` 逐批确认、区块边收边加入世界。

实测：行走 20 秒区块数 9 → **405**，修正次数 190+ → **2 次/20 秒**，速度不变。

**复查条件**：同类路径上修正次数降到接近 0 后关闭。**（已满足：区块流式加载后 2 次/15 秒）**

## R-资源包栈顺序（未核对）

- 概率：中；影响：高（顺序错会导致第三方包被内置包覆盖，表现为"装了包却没生效"）
- 事实：原版"靠后的包覆盖靠前的包"已核对（`FallbackResourceManager` 反向遍历）；**但客户端各来源（内置/目录/服务器）加入顺序与默认位置未逐行核对**。
- 缓解：先补核对（`ClientPackSource`、`Minecraft` 的 pack 注册、`DefaultPosition`），再冻结实现；核对结论写入 `docs/analysis/assets/resource-pack-stack.md` §5。
- 复查条件：ADR-0015 评审通过、包来源顺序确认后关闭。
