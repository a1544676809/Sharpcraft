# 渲染管线（规格）

本文件是渲染模块**下一阶段**的设计入口。已落地的部分（区块几何、贪婪合并、纹理图集、几何竞技场、
占位实体盒体）记录在 `docs/modules/render.md`，本文件不重复，只界定新的范围与边界。

> 实体渲染是**一个 pass**，不是整个模块。把模块理解成"渲染实体"会把天空、雾、半透明排序、
> 2D 合成与着色器包接入全部漏掉。

## 1. 范围

| 属于 | 不属于 |
| --- | --- |
| 地形几何、实体与方块实体、天空与雾、半透明与排序 | 世界模拟（服务端权威） |
| 2D 界面合成与其后的呈现 | 界面**布局与控件语义**（`docs/modules/ui.md`） |
| 后处理与外部着色器包的接入点 | Iris 具体文件格式的完整实现（`shader-packs.md` §6） |
| 帧预算、可见性剔除、缓冲区生命周期 | 音频、输入采集 |

## 2. 侧别与依赖方向

| 层 | 职责 | 约束 |
| --- | --- | --- |
| `Framework/Rendering` | WGPU 句柄、管线、缓冲区、提交 | **不认识**方块、实体、界面；只吃中性几何 |
| `Client/Render` | 从世界与实体表产出几何、组织 pass 顺序 | 只读世界与实体表，不反向依赖网络 |
| `Client/UI`（后续） | 产出 2D 顶点与绘制命令 | 经 `ui.md` §9 的 2D 契约进 `Framework` |

依赖方向由 `Architecture.Tests` 守护：`Framework` 不得引用 `Client`。中性几何载体目前是
`GeometryData`（静态）与 `DynamicGeometry`（每帧重建），二者都不含游戏类型。

## 3. 帧管线

单命令缓冲、单深度缓冲。阶段顺序固定，除 UI 外都写深度。

| # | Pass | 输入 | 深度 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 天空与雾 | 相机、渲染距离 | 关 | 全屏渐变，先铺底 |
| 2 | 不透明地形 | 区块竞技场切片 | 开 | 已在跑（§5.1） |
| 3 | 方块实体 | 世界中的方块实体列表 | 开 | 箱子/告示牌，P2 |
| 4 | 实体 | `EntityRenderState` 序列 | 开 | 占位盒体已跑（§6） |
| 4.5 | **Hi-Z 遮挡剔除** | 上一帧深度金字塔、候选 AABB | 关 | 规格见 `occlusion-culling.md`；O3 起生效 |
| 5 | 半透明 | 水/玻璃/半透明方块 | 开，不写深度 | 排序策略见 §7.1 |
| 6 | 名字牌/粒子 | 世界坐标 → 屏幕坐标投影 | 关 | 文字依赖 UI 模块 |
| 7 | 2D 界面 | UI 顶点流（20 字节） | 关 | ortho + 逐面板 scissor（`ui.md` §9） |
| 8 | 后处理 | 场景纹理、深度 | — | 默认直通；包的接入点见 §8 |
| 9 | 呈现 | 交换链纹理 | — | 与截图共用同一相机与几何 |

**每帧只允许一次场景提交**（`Frame` 内按顺序编码，一次 `Submit`），避免额外同步点。

## 4. 几何与缓冲区策略

| 几何种类 | 载体 | 生命周期 |
| --- | --- | --- |
| 区块几何（静态） | `ChunkGeometryArena` 每区块切片 | 常驻；尺寸不变时原地重写 |
| 每帧几何（实体盒体等） | `DynamicGeometry` + 独立双缓冲 | 每帧整块重写 |
| 2D 界面几何 | UI 顶点流（20 字节/顶点） | 每帧重建，复用缓冲 |
| 天空/后处理 | 全屏三角形，无需顶点缓冲 | 常量 |

三条硬性约束（已由实测确立）：`Queue.WriteBuffer` 要求 `CopyDst`；交换链纹理不保证可拷贝，
截图走离屏回读；窗口关闭时零尺寸帧必须提前 `break`，否则触发 `wgpuSurfaceConfigure` 校验错误。

## 5. 已实现部分的边界

### 5.1 区块几何

每区块一份网格，脏标记驱动重算；索引保持 0 基并用 `DrawIndexed(..., baseVertex, ...)`，
因此竞技场扩容只需搬顶点、不改索引。详见 `docs/modules/render.md` §5.2。

### 5.2 与 T-096 的关系

首帧是否需要等待区块，取决于世界由谁创建（§9）。渲染侧对此的要求只有一条：**世界为空时也必须能出帧**
（天空铺底 + 空几何），不得因缺区块而阻塞或崩溃。

## 6. 实体渲染

现状：每实体一个盒体（玩家 0.6×1.8 蓝色，其余 0.9×0.9 暖灰），24 顶点 / 36 索引，复用方块图集的
一格并靠顶点色区分；独立动态缓冲每帧整块重写，稳态零分配。

下一步（P1）：

| 项 | 方案 |
| --- | --- |
| 模型来源 | 运行时由启动器从 jar 提取模型 JSON 与纹理，**仓库内不存任何资产**（原则 3） |
| 模型解析 | 行为级重写：读 cube/uv/rotation 描述，产出与方块同布局的顶点 |
| 纹理 | 先并入现有图集；图集容量不够时再评估纹理数组（§7.3） |
| 朝向 | 已按原版约定换算（`LookConvention`）；模型的偏航/仰角直接复用 |
| 视锥剔除 | 每实体 AABB 与视锥求交，剔除计数进日志 |
| 名字牌 | 世界坐标 → 屏幕坐标，交给 UI 的文本渲染；本模块只提供投影 |

## 7. 未决项（需所有者裁决）

### 7.1 半透明排序（已裁决）

**先做按距离排序**（与原版同级：按区块/面到相机的距离从远到近）。交叉面仍可能出错，接受。
加权混合 OIT 等有明确需求再评估，不在 P2 范围。

### 7.2 模型动画范围（已裁决）

**P1 排除动画**：只做静态姿态 + 朝向。骨骼与动画状态机作为**独立切片**另行立项，
避免把渲染模块拖成"实体系统重写"。

### 7.3 图集与纹理数组（已裁决）

**先扩图集**（1024×1024 → 2048×2048，当前 1301 精灵余量充足）。一旦分块数逼近容量或单帧出现
图集切换，**立即改为分图集**（地形 / 实体各一），采样器绑定次数按此预留。纹理数组暂不引入。

### 7.4 渲染距离与模拟距离解耦

原版两者独立。我们目前按视距预分配竞技场；若要支持"渲染远、模拟近"，需要分层加载策略。

## 8. 外部着色器包接入

契约形状与失败规则已定稿于 `docs/specs/render/shader-packs.md`，本文件只声明**本模块必须提供的接入点**：

1. **渲染目标可被包覆盖**：天空、不透明、半透明、后处理各自是可命名的目标，而不是写死的交换链。
2. **阶段可被包插入/替换**：§3 的表格即阶段声明表，包按名字挂钩，不改引擎代码。
3. **采样与 uniform 可声明**：深度纹理、场景纹理、相机矩阵、时间、雾参数等以名字暴露。
4. **失败必须回退**：任何包侧编译失败都退回内置管线，**不得崩溃**（原则 11 硬要求）。

P3 之前不谈包；但 §3 的 pass 划分必须**现在就按"可命名目标"设计**，否则后面要返工。

## 10. 性能预算

沿用 `docs/specs/quality-attributes.md`：UI 层 0 B/帧、≤3 次提交、空闲帧布局 0 成本（QA-1.2）。
本模块新增的**提议值**（待评审确认后写入 QA-1）：

| 指标 | 提议阈值 | 测量方法 |
| --- | --- | --- |
| 每帧几何维护（CPU） | ≤ 2 ms | 帧内计时器累加并打日志 |
| 每帧实体几何重建 | 0 B/帧分配 | `GC.GetAllocatedBytesForCurrentThread` |
| 每帧提交次数 | ≤ 1（场景） | 计数器 |
| 区块/实体剔除 | 剔除率 ≥ 60%（放大世界） | 剔除计数日志 |
| 首帧时间 | ≤ 2 s（单次连接 + 9 区块） | 进程启动到首帧 |

## 13. 时域放缩前置能力（2026-10-30 所有者批准推进）

任何时域放缩器（自有 TAA/FSR 风格、或将来原生后端的 DLSS/XeSS）都需要**同一组**管线输出。
这些必须作为 §3 管线的一等能力存在，而不是事后补丁：

| 能力 | 要求 | 现状 |
| --- | --- | --- |
| **亚像素抖动** | 每帧对投影做 <1 px 的抖动，序列在一个小周期内均值归零 | **已实现**：`Client/Render/CameraJitter`（周期 8，`Apply` 以 clip 空间平移，4 项测试）|
| **运动矢量** | 逐像素屏幕空间位移（当前帧 → 上一帧），供历史样本重投影 | **数学部分已完成**：`Reprojection.Of/TryToScreen/ReconstructWorld/OfPixel` 与 `FrameHistory`（8 项测试，含像素级深度重建与解析解一致）；**GPU pass 待做**|
| **深度可采样** | 当前帧深度可作为纹理采样（不写回深度）| 部分（离屏有回读；窗口路径待确认）|
| **曝光/色调映射时机** | 放缩发生在 tonemap **之前** | 待定（P2 天空与雾时一并确定）|

约束：`Apply` 只平移投影矩阵第 3 行，**不得**改动视野、近远平面；抖动幅度超过 1 px 会造成画面明显抖动感。

## 15. 半透明阶段（实现计划，2026-10-30）

现状：网格里**没有**区分半透明几何（全仓无 render layer 分类），因此水/玻璃目前与不透明面同批绘制。

原版行为（§7.1 已裁决）：半透明在**不透明之后**绘制，**深度测试开、深度写关**，按**区块到相机距离从远到近**排序。

切片（每片可验证）：

| 片 | 内容 | 验证 |
| --- | --- | --- |
| S1 | 方块 → **渲染层**（opaque / translucent）分类；数据来自 blockstate 注册信息 | 单测：已知方块（水、玻璃、石头）分类正确 |
| S2 | 网格按层**拆成两份**（每区块 opaque + translucent 各一）| 单测：含水的区块产出两份网格、面数守恒 |
| S3（排序部分已完成）| 渲染顺序：opaque 全部 → translucent 按**距离降序**；混合开启、深度写关 | `TranslucentOrder.ByDistanceDescending`（3 项测试：最远优先、等距稳定、单元素）；出图验收待 S2 就绪 |
| S4 | 与天空/雾共用管线（雾同样作用于半透明）| 出图：远处水面融入雾色 |

已知近似（需登记为偏差）：区块内**不逐面**排序，只按区块排序（与原版粒度同级）；交叉面仍可能出错，§7.1 已接受。

依赖：S1 需要从资产/注册表取得方块渲染层信息（暂无），其余三片不依赖外部数据。

### S2 实施细节（已勘察代码，2026-10-30）

好消息：`ChunkMesher` 的**所有面都从同一个 `buffer.AppendQuad(...)` 出口写出**（`ChunkMesher.cs` L452 附近），
且该出口作用域里已有当前方块的 `state`。因此拆分不需要重写网格算法：

1. `MeshChunk(world, chunk, airState, buffer, maxBlocks, sprites, MeshBuffer? translucent = null, BlockStateLayout? layout = null)`；
2. 面出口改为 `var target = BlockRenderLayers.IsTranslucent(state, layout) ? (translucent ?? buffer) : buffer;`；
3. `Mesh(world, buffer, …)` 同步透传；`FrameCommand` 逐区块循环各建两个 `MeshBuffer`，得到两组 ranges；
4. `FrameRequest` 增 `TranslucentVertices/Indices/Ranges`；离屏再加一条**混合开、深度写关**的管线，在不透明之后绘制，
   ranges 按区块到相机距离**降序**（`TranslucentOrder` 已实现并有测试）。

验收：合成"两片半透明平面相交"场景，与"关闭半透明"渲染比对——被遮挡部分必须改变颜色，且不透明区域逐像素不变。

**S2 网格侧已完成（2026-10-30）**：`MeshChunk` / `MergeSectionFaces` / `EmitMergedQuad` 透传 `translucent` 缓冲与 `layout`，
面出口按 `BlockRenderLayers.IsTranslucent(state, layout)` 选目标缓冲。3 项测试：水入透明缓冲、无 layout 时全入不透明、
**拆分不改变总面数**。剩余：`FrameRequest` 双几何 + 混合管线 + 距离降序绘制。

**S2 渲染侧完成（2026-10-30）**：`BuildRequest` 增 `layout`（为空时回退 `VanillaBlockRegistry.Layout`），
`MC_FRAME_TRANSLUCENT=1` 时同一遍网格化同时填透明缓冲；离屏在 `pass.End()` 前用混合管线绘制。
合成"石头上覆水"场景实测：**透明层 10 个三角形，与"关闭透明"相比 97,344 个像素改变，首个 (324,114)**。

### 方块实体阶段：现状勘察（2026-10-30）

五阶段里只剩方块实体未开工。勘察结论（这是真正的门槛，不是渲染问题）：

1. `ChunkPacketParser` **目前只数个数、不保留数据**：`SkipBlockEntity`（`Common/Network/ChunkPacketParser.cs`，约 L228）
   读掉 `packed XZ`、`packed Y`、`type` 与 NBT 后丢弃，`ParsedChunk` 只记录 `BlockEntityCount` 与 `blockEntitiesSkipped`。
2. 因此客户端**没有任何方块实体实例**可用，渲染侧无论怎么写都拿不到要画的东西。
3. 需要先做数据侧：把 `(x, y, z, type)` 留在 `ParsedChunk` 里，再由世界装载进 `LevelChunk`。

**风险（需核实）**：`SkipBlockEntity` 的字段宽度是"先读 1 字节再读 2 字节"再读 VarInt，与注释所说的"packed XZ（2 字节）+ packed Y（2 字节）"
并不一致——它能跑通说明当前写法与真实字节流吻合，但**语义**（哪个字节是 x、哪个是 z、Y 是否要减 64）
必须与 `ref://mc-26.3-analysis` 的区块包读取实现核对后才能解码坐标，否则会把方块实体画到错误的方块位置。

**坐标编码已核对（2026-10-30）**，依据 `ref://mc-26.3-analysis/src/net/minecraft/network/protocol/game/ClientboundLevelChunkPacketData.java`：

| 字段 | 宽度 | 语义 |
| --- | --- | --- |
| `packedXZ` | **byte** | 高半字节 = 区块内 X，低半字节 = 区块内 Z（原版 `SectionPos.sectionRelative(packedXZ >> 4)` 与 `sectionRelative(packedXZ)`）|
| `y` | **short** | **绝对**方块 Y（无偏移）|
| `type` | VarInt | 方块实体类型注册表 id |
| `tag` | NBT | 可选 compound，缺席编码为单个 End 字节 |

⇒ 我原先"1 字节 + 2 字节"的读法**正确**，注释里"packed XZ 2 字节"是错的（已按参考纠正认知）。
`ParsedChunk` 现增 `BlockEntities`（`BlockEntityRecord(LocalX, Y, LocalZ, TypeId)`）。

**下一步**：`LevelChunk` 存储 → `BlockEntityMesher`（箱子 0.875³）→ 像素/数值验收。

### 混合从未真正启用（2026-10-30 纠错）

第 29/31 轮曾记录「混合管线已接线、有像素证据」。**这个结论不成立**：
