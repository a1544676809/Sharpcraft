# 性能基线（Performance Baseline）

AGENTS.md 原则 9：先有可复现基线，才谈优化；原则 12：性能需求必须"指标 + 阈值 + 测量方法 + 失败判定"。本文件记录**测量能力与实测数值**；阈值需项目所有者确认后写入 `docs/specs/quality-attributes.md`。

## 4. 已知噪声源（读数时必须考虑）

1. **网络**：B-6 含真实登录与服务端交互，抖动可达数秒，不得用于回归判定。
2. **JIT 与 GC**：首轮明显偏慢，故计 P50/P95 而非均值；`--warmup` 不足会让 P95 失真。
3. **GPU 驱动**：离屏渲染的耗时受驱动缓存影响，且首次建管线显著更慢，基准里单独标注冷/热。
4. **机器状态**：笔记本降频会整体抬高数值；跨机器比较无意义，只做同机前后对比。

## 5. 定阈值的建议（待所有者确认）

| 指标 | 建议阈值 | 依据 |
| --- | --- | --- |
| 区块包解析 | P95 ≤ 8 ms/包 | 一屏 9 区块需在 100 ms 内完成，留 10 倍余量 |
| 网格生成 | P95 ≤ 25 ms/区块 | 与 60 FPS 帧预算错开，避免移动时掉帧 |
| 裁剪空间变换 | P95 ≤ 2 ms/帧（11 万三角形规模） | 每帧必跑，需明显低于帧预算 |
| 稳态分配 | 0 字节/帧、0 字节/刻 | 原则 9 与 `[HotPath]` 已有约束 |
| 启动到首帧 | `[待定]` | 需先有资产管线才有意义 |

1. 任何"优化"提交 MUST 附本套件的同机前后对比；无对比的改动不视为优化。

## 7. 首次基线的主要发现（2026-10-28）

1. **网格生成是压倒性瓶颈**：9 区块 287k 方块一次 `Mesh` 的 P50 约 31 ms，但 **P95 达 184 ms**，最大与最小相差 6 倍；同一项每次运行分配 **14.8 MB**。方差来源是 `List<float>` / `List<uint>` 的反复扩容触发 GC，而不是 CPU 算术本身。优化方向明确：预计算容量 + `ArrayPool` 复用，目标是把单区块稳态分配压到 0。
2. **裁剪空间变换每帧分配 4 MB**：`float[]` 每次 `Build` 都新建。这是标准热路径问题，应改为复用缓冲（按帧写入池化数组），并在 `[HotPath]` 上加分配测试。
3. **解析与 NBT 都很便宜**：0.17 ms / 50 KB 与 0.004 ms 级别，说明协议层不需要优先优化。
4. **PNG 编码 13 ms**：只影响截图，不影响帧率；若将来需要录制/连续截图再优化（例如用固定 Huffman 表或跳过 zlib 最优压缩）。
5. **端到端（B-6）尚未纳入套件**：它包含网络，抖动过大，等资产管线就位再补；目前用 `launcher frame` 的阶段日志人工观察。

## 8. 首次优化前后对比（2026-10-28）

优化内容：网格生成改为池化 `MeshBuffer`（`ArrayPool`，不再用 `List` 扩容）+ 世界改为遍历已加载区块（不再扫 -512..512 的坐标窗口）；裁剪空间变换新增写入调用方 `Span<float>` 的重载，窗口路径用池化暂存。

| 项 | 优化前 P50 / P95 | 优化后 P50 / P95 | 优化前分配 | 优化后分配 |
| --- | --- | --- | --- | --- |
| 网格生成（一次性 API） | 30.8 / 183.6 ms | 21.8 / 132.9 ms | 14.8 MB | 4.3 MB |
| 网格生成（池化缓冲） | — | **20.8 / 22.2 ms** | — | **0 B** |
| 裁剪空间变换（数组版） | 2.05 / 2.42 ms | 1.89 / 2.21 ms | 4.0 MB | 4.0 MB |
| 裁剪空间变换（Span 版） | — | **1.47 / 1.78 ms** | — | **0 B** |

读数对比见 `benchmarks/results/2026-10-28-baseline.md` 与 `...-after-allocation-work.md`。

**结论与解读**：

1. 真正被消掉的是**尾部延迟**：池化网格的 P95 从 132.9 ms 降到 22.2 ms（最小/最大几乎重合成 19.6~22.2），说明此前 6 倍方差确实来自 GC 而非计算。
2. 一次性 API（返回 `MeshData`）仍要分配最终精确数组，因此保留 4.3 MB 与更长的尾巴；**热路径应调用池化重载**（`Mesh(world, buffer)`），一次性 API 只用于冷启动或测试。
3. 裁剪空间变换 Span 版同样把 P50 拉低 22%（1.89 → 1.47 ms），因为省掉了 4 MB 数组的清零与 GC 扫描。
4. 行为等效由 `ChunkMesherGoldenTests` 的三枚指纹（顺序无关）保证：优化前后三角形集合完全一致；`GeometryAllocationTests` 另行断言"暖缓冲下 0 分配"与"两条 API 输出一致"。

## 9. 光照与背面剔除的代价（2026-10-28）

网格生成现在每个方块要采样 6 次光照（每次 2 次字典查找 + nibble 解包）。实测同机对比：

| 项 | 加入光照前 P50 / P95 | 加入光照后 P50 / P95 | 结论 |
| --- | --- | --- | --- |
| 网格生成（池化，9 区块 287k 方块） | 20.8 / 22.2 ms | 23.5 / 24.5 ms | 约 +13%，换来了可读的明暗，性价比可接受 |
| 裁剪空间变换（Span） | 1.47 / 1.78 ms | 1.53 / 1.83 ms | 噪声范围内 |

读数见 `benchmarks/results/2026-10-28-lighting-and-culling.md`。背面剔除是 GPU 侧状态变更，CPU 侧不增加成本，减少的是片元着色与光栅化量（本套件不含 GPU 计时，故无数字）。

若后续需要压回光照成本，可选项：把 `TryGetLight` 的区块查找提到区块级循环外（每个区块一次），以及预先把 nibble 解包成每段 4096 字节的查找表。

## 10. 贪婪合并的代价与收益（2026-10-28）

| 项 | 合并前 | 合并后 | 变化 |
| --- | --- | --- | --- |
| 网格生成（池化，9 区块 287k 方块） | 23.5 ms P50 | 35.1 ms P50 | CPU **+49%** |
| 网格生成分配（池化） | 0 B | 0 B | 不变 |
| 网格生成分配（一次性 API） | 4.3 MB | 0.94 MB | **-78%**（四边形数量骤减） |
| 真实世界三角形数 | 110,868 | 51,402 | **-54%** |
| 本地演示世界三角形数 | 5,056 | 1,606 | **-68%** |

**解读**：合并用的是 CPU 换 GPU。网格生成发生在区块加载 / 方块变化时（一次性），三角形数是每帧都要付的，所以这笔交换对浏览中的客户端有利。

CPU 变贵的直接原因是每格要查两次世界（方块 + 光照）并且扩展时重复查询。若将来需要压回去，最直接的两条：

1. 采样格与本段同属一个段时，直接从 `ChunkSection` 取值，跳过 `ClientWorld` 的字典查找（多数情况属此类）；
2. 把 `(state, sky, block)` 预先缓存成每平面的键表，扩展时只比较整数。

按当前读数，单区块约 3.9 ms，仍低于 `quality-attributes.md` 里建议的 25 ms/区块阈值。


## 11. 启动首帧网格化耗时（T-793，2026-11-10 调查）

窗口路径首帧前的 `FrameCommand.BuildRequest` 独占启动时间（28–30 秒启动里 25–47 秒在这一段，随机器负载浮动），本轮只定位、不改行为。全部临时探针已删除。

### 11.1 分段实测（9 区块，`MC_VIEW_DISTANCE=32`）

| 段 | 累计 | 该段耗时 |
| --- | --- | --- |
| `EffectiveLighting` | 19 ms | 19 ms |
| `cache.Snapshot()`（合并已缓存网格，240,968 顶点） | 25 ms | 6 ms |
| **`cache is not null` 分支的二次网格化循环（9 区块）** | **44,593 ms** | **44,568 ms** |
| 三个图层 `ToMeshData` | 44,595 ms | 2 ms |
| `BoundsOf`（遍历全部顶点） | 44,596 ms | 1 ms |
| 半透明排序、雾色、构造请求 | 44,607 ms | 11 ms |

单区块耗时均匀（2.5–4.9 s/区块），不随已累计的几何增长。

### 11.2 与视距、区块数的关系

| 运行 | `BuildRequest` 时的区块数 | 二次网格化循环 |
| --- | --- | --- |
| `MC_VIEW_DISTANCE=32` | 9 | 44.6 s |
| 默认视距 | 9 | 47.5 s |
| `MC_START_CHUNKS=1` | 1 | 6.3 s |

与视距无关（预载恒停 9 个），与区块数近似线性（1 个 6.3 s，9 个 44.6 s），不是 O(n²)。

### 11.3 成因：缺少每 pass 预计算表，mesher 走回退路径

`ChunkMeshCache.Build` 每次 pass 只建一次 `StateCullTable`（每状态的面剔除表）与 `StateVisualCache`（每状态的精灵与图层缓存）并传给 `ChunkMesher.MeshChunk`；而 `BuildRequest` 的 `cache is not null` 分支直接调用便捷重载，**没有传 `cull`/`visuals`**。于是每一面都要走回退路径：`Occludes(...)` + `layout.BlockAt(state)?.Path` 的字典探测 + `EndsWith("_leaves")` 与字符串相等比较；每个四边形还要重新把状态解析成名字与精灵。

同一区块、同样几何（两个变体三角形数相同）的三方对照，同一进程内冷启动：

| 变体 | 耗时 | 分配 |
| --- | --- | --- |
| 现状（无表 + 有生物群系色调） | 4235 ms | 157 MiB |
| 有表 + 有色调 | 1068 ms | 7 MiB |
| 有表 + 无色调 | 1002 ms | 未测 |

表缺失占约 **3.2 s（75%）**；生物群系色调只占 66 ms（6%），不是主因。整轮循环共分配 **1.09 GB、89 次 gen0 GC**（9 区块），即回退路径的字典探测与逐次解析在大量分配。

### 11.4 结论与修复方向（下一轮实施）

- **成因类别**：热路径缺少每 pass 预计算表，导致每区块重复解析状态；既不是 O(n²)（每区块耗时均匀、总量线性），也不是同步等待（`cache.Snapshot()` 只用 6 ms，`pending=8` 表明后台工作池还在排队，这 45 s 是主线程纯 CPU）。
- **修复方向**：窗口路径复用同一张 `StateCullTable`/`StateVisualCache`，或让 `BuildRequest` 直接消费 `ChunkMeshCache.Layers` 已产生的分图层结果；顺带消掉"缓存已网格化、这里又网格化一遍"的重复劳动（`MC_START_CHUNKS=1` 时同一区块被网格化两次，白费 6.3 s）。
- **待查（本轮未测）**：即使有表，单区块冷启动仍需约 1 s，而本文档 §10 的池化基准是单区块 2.6 ms——差两个量级，可能来自冷 JIT、未池化缓冲与单线程。修完表后应重测一次基线再决定是否值得继续优化。
### 11.5 根治：请求只消费缓存，网格化只有一个入口（2026-11-10 已实施）

按 §11.3 的结论，窗口首帧请求**不再网格化任何区块**：`BuildRequest` 的 `cache is not null` 分支删除了那趟二次遍历，改为读缓存自己的产出——实心几何仍取自 `ChunkMeshCache.Snapshot()`（合并已缓存结果），半透明层取自缓存在网格化时顺手写入的 `LayerSinks.Translucent`；cutout 面按设计留在实心网格里，因此不再单独产出（旧代码那趟遍历额外生成的 cutout 层属于重复几何）。网格化入口经 `ChunkMeshCache.MeshChunkOnce` / `MeshWorldOnce` 收敛到 `Render/` 与后台工作池两处。

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 启动到首帧（同一台机器、`MC_VIEW_DISTANCE=32`） | **57.6 s** | **15.3 / 15.6 / 10.7 s**（三次，随机器负载波动） |
| `BuildRequest` 自身耗时 | ~44.6 s（9 区块二次网格化） | **17–26 ms**（`Snapshot` + 读图层 + `BoundsOf` + 雾色） |
| `mesh:`（首帧实心几何） | `1 blocks, 8606 triangles` | **完全一致** |
| `frame #0` 上传量 | `+7435 KiB` | **完全一致** |
| 首帧 `cull:` | `chunks=6 cutout=6 translucent=6` | **完全一致** |
| 几何来源 | 实心来自缓存 + 图层来自第二趟遍历 | 两者都来自缓存；稳态几何仍由工作池逐区块写入 arena（未被改动） |

首帧仍约 10–15 s，**未达到 5 s 目标**：分段探针显示 `BuildRequest` 内部每段合计仅 17–26 ms，剩余时间在请求构建之外——资源与连接约 1.5 s、网格预热约 0.6 s、另有约 7 s 稳定地出现在请求对象构造之后（已排除记录构造本身、`GameSettings`/光照/雾色/包围盒各段），渲染器启动到首帧约 3 s。这部分属独立任务，不应计入 T-793。

守门（防止复发）：

- `tests/Sharpcraft.Client.Tests/Render/FrameRequestDoesNotMeshTests.cs`：从缓存构建请求时 `ChunkMeshCache.TotalChunksMeshed` 不得增长，且返回的实心几何必须与 `Snapshot()` 逐项相等——直接锁住"请求不得网格化"。
- `tests/Sharpcraft.Architecture.Tests/SingleMeshingHomeTests.cs`：`MeshChunk(` / `ChunkMesher.Mesh(` 只允许出现在 `Render/ChunkMeshCache.cs` 与 `World/ChunkWorkerPool.cs`，第三个调用者即失败。
### 11.6 首帧里那 6.8 秒去哪了（T-794，2026-11-10 复查）

§11.5 修复后仍观察到"请求构造之后有一段约 6.8 秒的稳定空白"。本轮用进程年龄探针复查（临时探针已删净）：

| 时间点（进程年龄） | 运行 1 | 运行 2 |
| --- | --- | --- |
| `RunAsync` 入口 | 153 ms | 146 ms |
| 资源管理器 + 精灵表就绪 | 378 ms | 383 ms |
| **首帧请求构建完成** | **7604 ms** | **6680 ms** |
| 之后的所有客户端侧准备（语言、聊天类型、生物群系、会话、云纹理、天体/UI 精灵） | +267 ms | +259 ms |
| 窗口创建 | +537 ms | +573 ms |
| wgpu 实例 / surface / adapter / device | +1008 ms | +1015 ms |
| 管线、图集上传、首帧 | +1117 ms | +935 ms |

结论：

- **6.8 秒的空白没有复现**：从"请求构建完成"到"首帧呈现"合计 **2.78–2.93 s**，且各段平滑、没有孤立的停顿。该空白只在 §11.5 修复前的构建上出现过，而那段时间紧接在 1.09 GB 的分配风暴之后——**归因于那次分配引发的一次性 GC / 堆增长（类别 ②）**，随 T-793 一并消失。没有找到"白干"（无重复工作、无无意义等待），因此本轮不修改代码。
- **当前真正的启动大头不在渲染侧**：请求完成前已过去 6.7–7.6 s，其中"资源管理器就绪"只占 0.38 s，**剩下约 6.3–7.2 s 全部落在登录 + 配置握手 + 区块预载**（同一台机器、同一服务器，早些时候该段只需约 1.3 s，说明它随服务器/网络状态波动）。渲染侧总计 2.8–3.0 s，其中约 1.0 s 是不可避免的首次设备/管线/上传工作。
- **下次再看这事的条件**：若要继续压启动时间，应先测"登录 + 配置 + 预载"这一段（它与服务器状态强相关，需要单独的真值口径），而不是渲染侧——渲染侧已无可去除的停顿。
- 复查所用的三维对照（几何与首帧数据）在本轮保持稳定：`mesh: 1 blocks, 8606 triangles`、`frame #0 uploaded +7435 KiB`、首帧 `cull: chunks=6 cutout=6 translucent=6` 与 §11.5 完全一致。
## 12. 渲染帧时间归因（T-796，2026-11-10）

### 12.1 方法

三样装置，全部经 `FrameDiagnostics` 由宿主显式打开（原则 13：渲染器不读环境变量）：

| 装置 | 开关 | 输出 |
| --- | --- | --- |
| 分段 CPU 计时 | `MC_FRAME_CPU=1` | `frame-cpu: n=… frame=… updates=… acquire=… camera=… scene=… oit=… text=… clouds=… ui=… present-rec=… submit=… present=… skip=…`（每秒一条，是最近 60 帧的均值） |
| 跳过参考 OIT | `MC_SKIP_OIT=1` | 只跑不透明/切边 pass 与上屏拷贝 |
| 跳过云 | `MC_SKIP_CLOUDS=1` | 云几何、云 pass、云 OIT 阶段全部不画 |
| 跳过半透明 | `MC_SKIP_TRANSLUCENT=1` | 只去掉半透明地形绘制（上传照旧） |

脚本 `tools/verify/measure-frame.ps1` 固定机位（`tp <player> -74.098 121 37.303 180 1.5`）、854×480、视距 32、`MC_PRESENT_MODE=immediate`，按"默认 → 跳 OIT → 跳云 → 跳半透明"各跑一次，传送后静置再采样，输出 CSV 对照表。

**口径说明**：每行是一个独立进程，四行在同一次会话内背靠背运行；绝对值随机器的电源/频率状态漂移（同一构建两次运行默认行 10.5 ms 与 15.1 ms），**只能行间比较**。

### 12.3 结论

- **帧时间的约 70% 是 GPU 侧，CPU 只占约 2.6–4.5 ms**。判据是 `acquire`、`submit`、`present` 三段：它们本身不做工作，是等待上一帧的 GPU 完成（交换链图像未释放、队列满）。默认行 5.7 + 3.0 + 1.9 ≈ 10.6 ms；跳掉 OIT 后同样的三段收缩到 1.3 + 1.1 + 1.5 ≈ 3.9 ms。
- **最大单项是参考 OIT 的半透明序列**：跳掉它省 7.7–8.5 ms（50%–56%），跳掉半透明几何本身省 7.7 ms（50.6%）——两者几乎相等，说明代价几乎全在"把半透明几何重画三遍（bounds / transmittance / accumulate）"上，而不是 pass 之间的固定开销。
- **CPU 侧最大的两项是 `updates`（1.0–1.5 ms，几何上传 + arena 应用）与 `scene`（1.1–1.5 ms，不透明/切边/实体的命令录制）**；相机采样 0.08–0.14 ms，UI 录制约 0.01 ms，世界文字 0.06 ms，上屏拷贝录制 0.007 ms。
- **云不是大头**：0.6 ms（4%）–1.1 ms（11%）。

### 12.4 A/B 法分不开的部分（需另想办法）

- **OIT 内部各 pass 的占比**（bounds / cull / cloud bounds / transmittance / accumulate / composite）：现有开关只能整体跳，跳 OIT 与跳半透明的差值（0.9 ms）小于噪声，切不开。需要 GPU timestamp query，或给 `FrameDiagnostics` 加"只跑 N 个阶段"的更细开关。
- **不透明地形与实体各自的 GPU 成本**：没有开关能把它们分开（关掉其中一个会改变画面到无法比较），且切边层与不透明层共用同一 depth，拆开需要改 pass 结构。
- **CPU `submit` 究竟花在 CPU 还是等 GPU**：`backend.Submit` 内部若队列未满会立即返回；当前它随 GPU 负载同步升降，倾向"在等"，但要用队列水位才能确证。
- **`acquire` 与 `present` 的划分**：两者都在等交换链，单独拆开需要 wgpu 的 fence 计时。

### 12.5 复现方式

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/verify/measure-frame.ps1 -SettleSeconds 75 -SampleSeconds 20
```

`-Only default|skip-oit|skip-clouds|skip-translucent` 可单跑一行；`-SkipTeleport` 用于保持当前位置。脚本按行输出 CSV，并给出相对默认行的差值百分比。
