# 性能基线（Performance Baseline）

AGENTS.md 原则 9：先有可复现基线，才谈优化；原则 12：性能需求必须"指标 + 阈值 + 测量方法 + 失败判定"。本文件记录**测量能力与实测数值**；阈值需项目所有者确认后写入 `docs/specs/quality-attributes.md`。

## 1. 测量工具

| 工具 | 位置 | 说明 |
| --- | --- | --- |
| 基准套件 | `benchmarks/MinecraftCSharp.Benchmarks` | 控制台程序，纯自研计时（不引入 BenchmarkDotNet，避免额外依赖与噪声） |
| 计时口径 | 同上 | 先做 `Warmup` 轮，再采样 `Iterations` 轮；报告 P50 / P95 / 最小 / 最大；分配量用 `GC.GetAllocatedBytesForCurrentThread` 前后差 |
| 端到端阶段计时 | `MinecraftCSharp.Launcher frame` | 认证 / 收区块 / 网格 / 离屏渲染 / PNG 编码各自耗时 |

运行方式：

```
dotnet run -c Release --project benchmarks/MinecraftCSharp.Benchmarks
```

可选参数：

| 参数 | 作用 |
| --- | --- |
| `--iterations N` | 每项的采样轮数（默认 20） |
| `--warmup N` | 预热轮数（默认 3） |
| `--real <path>` | 用本地捕获的真实区块包替换合成数据（该文件不得进仓库） |

| --- | --- | --- | --- |
| B-1 | 区块包解析 | `ChunkPacketParser.TryRead` 一包耗时与分配 | 进服瞬间的突发负载，直接影响"能否及时显示地形" |

## 4. 已知噪声源（读数时必须考虑）

1. **网络**：B-6 含真实登录与服务端交互，抖动可达数秒，不得用于回归判定。
2. **JIT 与 GC**：首轮明显偏慢，故计 P50/P95 而非均值；`--warmup` 不足会让 P95 失真。
3. **GPU 驱动**：离屏渲染的耗时受驱动缓存影响，且首次建管线显著更慢，基准里单独标注冷/热。
4. **机器状态**：笔记本降频会整体抬高数值；跨机器比较无意义，只做同机前后对比。

## 5. 定阈值的建议（待所有者确认）

| 指标 | 建议阈值 | 依据 |
| --- | --- | --- |
| 区块包解析 | P95 ≤ 8 ms/包 | 一屏 9 区块需在 100 ms 内完成，留 10 倍余量 |
| 网格生成 | P95 ≤ 25 ms/区块 | 与 60 FPS 帧预算错开，避免移动时掉帧 |
| 裁剪空间变换 | P95 ≤ 2 ms/帧（11 万三角形规模） | 每帧必跑，需明显低于帧预算 |
| 稳态分配 | 0 字节/帧、0 字节/刻 | 原则 9 与 `[HotPath]` 已有约束 |
| 启动到首帧 | `[待定]` | 需先有资产管线才有意义 |

## 6. 使用规则

1. 任何"优化"提交 MUST 附本套件的同机前后对比；无对比的改动不视为优化。
2. 阈值确认后写入 `docs/specs/quality-attributes.md`，本文件继续只记数值与方法。
3. 变更测量方法属于规格变更，需 ADR（原则 12）。

## 7. 首次基线的主要发现（2026-10-28）

1. **网格生成是压倒性瓶颈**：9 区块 287k 方块一次 `Mesh` 的 P50 约 31 ms，但 **P95 达 184 ms**，最大与最小相差 6 倍；同一项每次运行分配 **14.8 MB**。方差来源是 `List<float>` / `List<uint>` 的反复扩容触发 GC，而不是 CPU 算术本身。优化方向明确：预计算容量 + `ArrayPool` 复用，目标是把单区块稳态分配压到 0。
2. **裁剪空间变换每帧分配 4 MB**：`float[]` 每次 `Build` 都新建。这是标准热路径问题，应改为复用缓冲（按帧写入池化数组），并在 `[HotPath]` 上加分配测试。
3. **解析与 NBT 都很便宜**：0.17 ms / 50 KB 与 0.004 ms 级别，说明协议层不需要优先优化。
4. **PNG 编码 13 ms**：只影响截图，不影响帧率；若将来需要录制/连续截图再优化（例如用固定 Huffman 表或跳过 zlib 最优压缩）。
5. **端到端（B-6）尚未纳入套件**：它包含网络，抖动过大，等资产管线就位再补；目前用 `launcher frame` 的阶段日志人工观察。

## 8. 首次优化前后对比（2026-10-28）

优化内容：网格生成改为池化 `MeshBuffer`（`ArrayPool`，不再用 `List` 扩容）+ 世界改为遍历已加载区块（不再扫 -512..512 的坐标窗口）；裁剪空间变换新增写入调用方 `Span<float>` 的重载，窗口路径用池化暂存。

| 项 | 优化前 P50 / P95 | 优化后 P50 / P95 | 优化前分配 | 优化后分配 |
| --- | --- | --- | --- | --- |
| 网格生成（一次性 API） | 30.8 / 183.6 ms | 21.8 / 132.9 ms | 14.8 MB | 4.3 MB |
| 网格生成（池化缓冲） | — | **20.8 / 22.2 ms** | — | **0 B** |
| 裁剪空间变换（数组版） | 2.05 / 2.42 ms | 1.89 / 2.21 ms | 4.0 MB | 4.0 MB |
| 裁剪空间变换（Span 版） | — | **1.47 / 1.78 ms** | — | **0 B** |

读数对比见 `benchmarks/results/2026-10-28-baseline.md` 与 `...-after-allocation-work.md`。

**结论与解读**：

1. 真正被消掉的是**尾部延迟**：池化网格的 P95 从 132.9 ms 降到 22.2 ms（最小/最大几乎重合成 19.6~22.2），说明此前 6 倍方差确实来自 GC 而非计算。
2. 一次性 API（返回 `MeshData`）仍要分配最终精确数组，因此保留 4.3 MB 与更长的尾巴；**热路径应调用池化重载**（`Mesh(world, buffer)`），一次性 API 只用于冷启动或测试。
3. 裁剪空间变换 Span 版同样把 P50 拉低 22%（1.89 → 1.47 ms），因为省掉了 4 MB 数组的清零与 GC 扫描。
4. 行为等效由 `ChunkMesherGoldenTests` 的三枚指纹（顺序无关）保证：优化前后三角形集合完全一致；`GeometryAllocationTests` 另行断言"暖缓冲下 0 分配"与"两条 API 输出一致"。

## 9. 光照与背面剔除的代价（2026-10-28）

网格生成现在每个方块要采样 6 次光照（每次 2 次字典查找 + nibble 解包）。实测同机对比：

| 项 | 加入光照前 P50 / P95 | 加入光照后 P50 / P95 | 结论 |
| --- | --- | --- | --- |
| 网格生成（池化，9 区块 287k 方块） | 20.8 / 22.2 ms | 23.5 / 24.5 ms | 约 +13%，换来了可读的明暗，性价比可接受 |
| 裁剪空间变换（Span） | 1.47 / 1.78 ms | 1.53 / 1.83 ms | 噪声范围内 |

读数见 `benchmarks/results/2026-10-28-lighting-and-culling.md`。背面剔除是 GPU 侧状态变更，CPU 侧不增加成本，减少的是片元着色与光栅化量（本套件不含 GPU 计时，故无数字）。

若后续需要压回光照成本，可选项：把 `TryGetLight` 的区块查找提到区块级循环外（每个区块一次），以及预先把 nibble 解包成每段 4096 字节的查找表。

## 10. 贪婪合并的代价与收益（2026-10-28）

| 项 | 合并前 | 合并后 | 变化 |
| --- | --- | --- | --- |
| 网格生成（池化，9 区块 287k 方块） | 23.5 ms P50 | 35.1 ms P50 | CPU **+49%** |
| 网格生成分配（池化） | 0 B | 0 B | 不变 |
| 网格生成分配（一次性 API） | 4.3 MB | 0.94 MB | **-78%**（四边形数量骤减） |
| 真实世界三角形数 | 110,868 | 51,402 | **-54%** |
| 本地演示世界三角形数 | 5,056 | 1,606 | **-68%** |

**解读**：合并用的是 CPU 换 GPU。网格生成发生在区块加载 / 方块变化时（一次性），三角形数是每帧都要付的，所以这笔交换对浏览中的客户端有利。

CPU 变贵的直接原因是每格要查两次世界（方块 + 光照）并且扩展时重复查询。若将来需要压回去，最直接的两条：

1. 采样格与本段同属一个段时，直接从 `ChunkSection` 取值，跳过 `ClientWorld` 的字典查找（多数情况属此类）；
2. 把 `(state, sky, block)` 预先缓存成每平面的键表，扩展时只比较整数。

按当前读数，单区块约 3.9 ms，仍低于 `quality-attributes.md` 里建议的 25 ms/区块阈值。
