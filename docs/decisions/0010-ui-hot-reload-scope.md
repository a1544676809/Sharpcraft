# 0010：界面热加载的范围与边界

- 状态：已接受
- 日期：2026-10-29
- 决策者：项目所有者（"发布版带完全的热加载能力"、"固定路径，根源上不提供未受管路径"）
- 关联：`docs/modules/ui.md` §8、§8.1；原则 2（模组热加载）、原则 9（可观测行为对齐）

## 背景

界面层需要一个迭代回路：改布局或文案后立即可见。业界常见做法（WPF / WinUI）只在**调试模式**提供
XAML 热加载。需要判断这一限制是否适用于本项目，以及热加载应该开放到什么范围。

## 决策

1. **界面文档热加载在发布版恒可用**，由一个运行时开关（`off`）可以关闭，但**不按构建配置分化**。
2. **模组程序集热加载恒开**，与构建配置无关（原则 2 的要求）。
3. **只从受管路径读取**：`<用户数据目录>/ui/main.xaml`（本客户端）与显式注册的模组界面目录。
   **不提供任何未受管路径的加载能力**——不设环境变量、不设命令行选项指向任意文件。
4. **不得改为构建期编译**：若将来为了性能引入文档的预编译，必须发生在**加载时**，而不是构建时。

## 理由

### 为什么可以不像 WPF / WinUI 那样限定调试模式

那一类框架的 XAML 是**编译期产物**（BAML / 生成代码），运行时没有"重新解析这份文档"的入口，热加载依赖
IDE 注入与调试器附加；发布版还会裁剪反射元数据、AOT 编译、固化编译绑定，使重载在架构上不可能。

本项目相反：文档是**运行期解释**的，`UiNode` 树与 `UiStyles` 在加载时产生，布局与几何每帧重建，
GPU 侧的管线与绑定组与文档无关。因此"发布版不能热加载"在这里不是安全考虑，而是**没有那个技术前提**。

### 为什么不按构建配置分化

- 两条代码路径意味着发布版那条**永不执行、永不测试**，几个月后必然腐坏——与"用 pragma 压警告"同类错误。
- 收益接近零：稳态成本是一次引用读；失败由"保留上一屏"兜住；监听器只是一个句柄 + 一次去抖定时器。
- 模组作者需要它：模组界面在发布版能改即时生效才有可用的迭代回路。

### 为什么必须限定受管路径

发布版带热加载意味着**本机任何能写该目录的进程**都能替换运行中游戏的界面。这不是内存安全问题，而是
**社会工程面**：一块"请重新登录 Microsoft 账号"的假面板，比任何漏洞都更容易得手。
因此路径是固定的，越界即拒绝（`UiDocumentFile.IsManaged`），并且不提供"指向别处"的开关。

### 为什么"加载时编译"必须写进决策

如果哪天为了性能把文档改成构建期源生成（编译进程序集），就会重新落入 WPF/WinUI 的困境——发布版
自动失去热加载，而且没人会注意到，直到用户抱怨。写成硬约束，是为了让那次"优化"必须先回答这个问题。

## 后果

- 发布版与开发版行为一致，热加载路径始终被真实使用；没有"只在开发机可用"的分类。
- 需要长期维护一份**可测判据**（`docs/modules/ui.md` §8.1 的七条），否则"恒可用"会退化为"偶尔能用"。
- UI 仿冒面被限定在用户数据目录内；若将来支持模组界面目录，该目录同样必须由启动器登记并校验。
- 关闭能力保留为运行时开关，用于整合包分发与故障排查，不用于区分开发者与玩家。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 仅调试模式（`#if DEBUG` 或"开发模式"启动参数）| 双代码路径、发布版不被使用、模组作者无法在发布版迭代 |
| 允许 `--ui-file <任意路径>` | 把 UI 仿冒面扩大到整块磁盘，且与"固定路径"决策冲突 |
| 构建期把文档编译进程序集 | 发布版失去热加载，且退化是静默的 |
| 不做失败保留（坏文件即清屏）| 编辑器保存瞬间的半写文件会让界面闪空 |
