# 0011：接受大块地形到达时的单帧上传尖峰

- 状态：已接受
- 日期：2026-10-29
- 决策者：项目所有者（"先选 B 好些，毕竟大块地形到达的场景屈指可数"）
- 关联：`docs/specs/quality-attributes.md` 帧尖峰归因；原则 9（性能驱动的偏差须记录并评审）

## 背景

自动化帧统计（`docs/specs/quality-attributes.md`）显示：1801 帧中 6 帧（0.3%）超过 33 ms，
最差 60.1 ms，且慢帧现场日志证明**不是 GC**，而是**单帧内无上限的区块几何上传**——最差那一帧一条更新就搬了 97 MB。

两条候选修法：按字节预算切片上传（地形晚出现约 0.4 s，需"进行中上传"状态），或接受并记录为受控偏差。

## 决策

**接受该尖峰，记录为受控偏差。** 不实现切片上传。

## 理由

- 尖峰只在**大块地形一次性到达**时出现，这种场景在正常游玩中屈指可数；
- 尖峰期间**不丢帧**（整体仍维持约 60 fps），观感是"一次轻微的停顿"而非卡死；
- 切片上传的代价是实打实的：需要"进行中上传"状态机、跨帧续传、以及与区块重建的交互，复杂度与收益不成比例；
- 原版本体在大块地形到达时同样有可感知的停顿，因此这**不构成与原版的可观测行为差异**。

## 后果

- `QA-1.3` 的帧时间预算保留为"目标"，并新增一条**受控偏差**条目：单帧上传不设上限，允许大块地形到达时出现数十毫秒尖峰。
- 慢帧现场的日志（`frame #N gap … updates … uploaded … gc …`）**保留**，作为复查手段：若尖峰频率上升或场景泛化（例如多帧连续超限），须重新评审。
- 若将来引入后台线程上传或 GPU 侧流式上传，本偏差应随之撤销。

## 复查条件

满足任一即重新评估（改回切片上传）：

1. 超过 33 ms 的帧占比 > 2%（当前 0.3%）；
2. 出现连续 3 帧以上超限（当前为孤立帧）；
3. 尖峰出现在**没有**大块地形到达的时段。
