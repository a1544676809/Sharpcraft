# UI —— 界面层

把界面拆成**声明式的结构与外观**（文件，可热加载）与**代码化的行为**（程序集，可热重载）两半，
并在单一 2D 批次里绘制，做到"改一个像素不用重新编译，改一段逻辑不用重启"。

## 1. 职责范围

负责：

- 屏幕栈与生命周期（打开 / 渲染 / 每刻更新 / 关闭 / 暂停世界输入）
- 控件树（容器、标签、按钮、输入框、列表、物品槽）与布局
- 声明式界面的解析、校验、版本兼容与热加载交换
- 界面绘制：正交投影、纹理与形状批次、裁剪栈、位图字体排版
- 输入路由：命中测试、焦点、捕获（拖拽）、键盘导航；**首批只支持键盘与鼠标**（所有者 2026-10-29 决定）
- 与游戏逻辑的**只读**接线（血量、物品栏、聊天记录、玩家列表）

明确不负责：

- 世界渲染与区块网格（`docs/modules/render.md`）
- 输入采集与动作映射（`docs/modules/input.md`）；本层只消费动作后的状态
- 游戏规则（背包容量、合成、聊天命令语义）——这些属于 `Common` 的玩法层
- 字体、控件贴图等资产本体：一律由启动器从用户本地 jar 提取（原则 3），仓库内只有加载逻辑

## 2. 侧别归属

- 归属：`Client`
- 判定依据：界面是纯客户端表现，不参与权威世界状态；服务端只传输容器内容、聊天与玩家列表等数据，
  由客户端决定如何呈现。与 `docs/architecture/boundaries.md` 的"Client 负责渲染 / 输入 / UI"一致。

## 3. 依赖关系

| 方向 | 对象 | 说明 |
| --- | --- | --- |
| 依赖 | `Framework.Rendering` 的 **2D 批次原语** | 只依赖批次与纹理句柄抽象，不接触 WGPU 类型 |
| 依赖 | `Common` 的数据结构 | 物品栈、聊天消息、玩家列表条目等只读数据 |
| 依赖 | `Client/Assets` | 图集、位图字体、控件贴图的解析结果 |
| 被依赖 | `Modding` 的界面扩展契约 | 模组注册控件与屏幕，只经公开接口 |
| 被依赖 | 启动层（`Sharpcraft.Launcher` 的 `window` 路径） | 打开屏幕、转发输入 |

依赖方向自检：不出现 `Client ↔ Server` 直引；界面层不引用启动器与资产提取器等外围宿主层；
`Framework` 不反向引用 `Client`。

## 4. 对外契约

- 接口：`IUiScreen`（生命周期）、`IUiWidget`（测量 / 布局 / 绘制数据 / 命中测试）、`IUiHost`（打开 / 关闭 / 交换）
- 数据：`UiMarkupDocument`（不可变、已校验）、`UiDrawList`（本帧绘制数据）、`UiMetrics`（性能计数器）
- 事件：屏幕开闭、控件激活、文本提交、滚动、拖拽开始 / 移动 / 放下、热加载成功 / 失败
- 明确不暴露：控件内部的 GPU 资源、解析器的中间状态、WGPU 句柄（原则 6）、其他控件的可变字段

## 5. 关键数据结构

| 结构 | 性质 | 说明 |
| --- | --- | --- |
| `UiMarkupDocument` | 不可变 | 解析 + 校验后的声明式文档；含 schema 版本 |
| `UiNode` | 不可变 | 元素 + 属性 + 子节点 + 绑定的行为处理器名 |
| `UiWidget` | 可变、池化 | 实例化后的控件；只在交换或结构变更时重建 |
| `UiLayout` | 可变、池化 | 由控件树一次算出的矩形，供命中测试与绘制共用 |
| `UiDrawList` | 每帧复用 | 四边形、文本运行、裁剪区间；**不分配** |
| `UiTextRun` | 每帧复用 | 一段同一样式的文本；富文本由多段组成（颜色、粗体、点击事件） |
| `UiGlyphAtlas` | 常驻 | 位图字体按需烘焙的字形；命中率可观测 |
| `UiMetrics` | 常驻 | 布局次数、提交次数、四边形数、分配字节、解析耗时 |

## 6. 每帧运行流程

```
文件变化（可选） → 后台解析 + 校验 → 原子交换（迁移状态）
        ↓
输入路由（命中测试 → 焦点 → 捕获）           ← 每帧
        ↓
布局（仅脏时执行，单趟）                       ← 空闲帧 0 次
        ↓
构建绘制列表（控件只追加数据，不发绘制调用）    ← 每帧，池化
        ↓
排序 + 合批（layer → 材质 → 裁剪）→ ≤3 次提交  ← 每帧
```

约束：

- **控件不发绘制调用**：这是性能上限与可维护性的共同前提，避免每个控件各自切换管线状态。
- **布局只在脏时执行**：控件树结构、尺寸、文本内容变化才置脏；空闲帧必须为零次。
- **文本排版缓存**：按（字符串、样式、可用宽度）缓存行布局，内容不变不重算。

## 7. 声明式格式：XAML

语法与**微软系产品一致，采用 XAML**（所有者 2026-10-29 决定）。注意这是**XAML 语言本身**，
不是 WPF 的 XAML 实现：我们自研加载器，不引用 WPF / WinUI（跨平台不可用，且违反原则 6 的后端隔离）。

采用 XAML 的理由：命名空间声明、属性元素、内容属性、标记扩展（`{Binding}`、`{StaticResource}`）
都是现成约定，写界面的人不必学一套新语法；编辑器也有现成的高亮与格式化。

```xml
<Screen xmlns="https://sharpcraft.dev/ui" xmlns:x="https://sharpcraft.dev/ui/xaml"
        x:Class="Sharpcraft.Client.Ui.Screens.ChatScreen" Id="chat">
  <StackPanel Anchor="Bottom" Margin="8">
    <RichText Id="messages" Grow="1" Bind.Text="{Binding Messages}"/>
    <TextBox Id="input" Hint="chat.hint" Submit="SendChat"/>
  </StackPanel>
</Screen>
```

约定的最小面：

- **元素 = 控件类型**，**属性 = 控件属性**；大小写与 .NET 类型/属性一致
- `x:Class` 指向行为侧类型（可选）；有它时可省略属性里的事件名绑定
- 事件与命令以字符串绑定到具名处理器（`Submit="SendChat"`），行为留在代码
- 标记扩展首批只支持两种：`{Binding 路径}`（单向到数据源）与 `{StaticResource 键}`（样式/贴图）
- 文案一律走本地化键；元素与属性名用英文

范围控制：

- 首批控件类型限于 `Screen / StackPanel / Grid / Panel / TextBlock / RichText / Button / TextBox / List / Item / Image`
- **不实现**依赖属性系统的完整语义（样式继承、触发器、模板重写）；需要时以代码屏幕解决
- 未知元素或未知属性 = **可定位的报错**；文档必须带架构版本，解析失败**原子回退**到上一份可用文档
- 解析在后台线程完成；**渲染线程不解析任何文件**

## 8. 热加载边界

| 变化内容 | 机制 | 是否重启进程 |
| --- | --- | --- |
| 布局、间距、样式、贴图引用、文案键 | 文件监听 → 后台解析 → 帧边界原子交换 | 否 |
| 行为（处理器、数据绑定逻辑） | 程序集热重载（原则 2 的 collectible ALC） | 否 |
| 控件类型本身 | 同上（控件属于行为侧） | 否 |

交换语义：

- 交换发生在**帧边界**，本帧要么全旧要么全新，不出现半更新状态
- 交换时按控件 `id` 迁移滚动位置、输入框内容、焦点与捕获状态
- 结构不可迁移时（例如控件被删除）允许丢弃该控件的状态，但**不得**让屏幕整体失效

### 8.1 实现规格（2026-10-29）

适用构建与路径边界见 **ADR-0010**：发布版恒可用、单一开关可关、**只从受管路径读取**。

| 层 | 机制 | 约束 |
| --- | --- | --- |
| 触发 | `FileSystemWatcher`（`LastWrite`/`Size`/`FileName`）| 不轮询 mtime：那是每帧一次系统调用 |
| 去抖 | 150 ms 静止后才读 | 编辑器保存是多次写 |
| 稳定窗口 | 间隔 60 ms 读两次，长度一致才接受 | 半写文件不得进屏幕 |
| 解析 | 后台任务，带**代次号** | 渲染线程解析次数 = 0 |
| 交换 | `Interlocked`/`Volatile` 交换一个不可变 `CompiledScreen(Root, Styles)` | 树与样式表必须一起换（样式表按节点引用查表）|
| 启动 | **同步**读一次（调用方据此决定是否用内置兜底屏）| 帧路径仍不解析，只在启动时阻塞一次文件读 |
| 采用 | 每帧只读一个引用 | 稳态 0 分配 |
| 失败 | 保留上一屏 + 记 `LastError` + 计数；**启动时就不合法则用内置屏兜底** | 不得整屏失效，也不得启动即空白 |
| 可见性 | 每次接受打印 `ui: applied document`，每次拒绝打印原因 | 改了没生效与改动太小看不见要能区分 |

**七条可测判据**

| 判据 | 方法 | 阈值 |
| --- | --- | --- |
| 稳态零成本 | 分配计数 + 解析计数 | 0 B/帧；渲染线程解析 0 次 |
| 重载延迟 | 保存 → 生效时间戳差 | < 300 ms（含去抖与稳定窗口）|
| 解析成本 | 50 节点文档 | < 2 ms |
| 坏文件 | 20 份畸形文档（截断/错标签/未知属性/超大/深嵌套）| 0 崩溃、0 整屏失效，全部记录原因 |
| 半写文件 | 写一半 → 间隔 → 写完 | 不出现半屏 |
| 压力 | 连续 1000 帧每帧交换 | 无分配尖峰、无崩溃 |
| 状态迁移 | 只改样式不改结构 | 滚动位置/焦点保持（T-103b）|

**判据自动化（T-109）**：其中五条已由 `UiHotReloadCriteriaTests` 守护——五十节点文档编译耗时、
二十份畸形文档全部拒绝且不上屏、二十份半写文档拒绝、一千次交换不抛且帧预算不失控、以及**构建帧不触碰加载器**
（渲染线程解析数恒为 0）。另两条（真实文件监听延迟、状态迁移）需要 T-108 与集成环境。

**结构校验在加载期完成**：`<TextBlock><TextBlock/></TextBlock>` 这类能解析但无法布局的文档，
必须在加载时拒绝——否则异常会在**构建帧**时抛出，而那是渲染线程。

**边界（与 ADR-0010 一致）**：只接受 `<用户数据目录>/ui/main.xaml` 与已登记的模组界面目录；
`UiDocumentFile.IsManaged` 拒绝任何越界路径；**不提供指向任意文件的开关**。

### 8.3 玩家列表规格（对齐原版）

界面框架是我们自己的，但**行为必须等效**：排序、上限、列布局、延迟阈值都照原版来，否则"用不同代码画出不同的延迟"本身就是行为偏离。
证据：`ref://mc-26.3-analysis/src/net/minecraft/client/gui/components/PlayerTabOverlay.java`。

| 项 | 原版规则 |
| --- | --- |
| 数据 | 只取 `listed` 的在线玩家 |
| 排序 | ①`listOrder` 降序 ②旁观者（游戏模式 3）排最后 ③队伍名 ④名字忽略大小写 |
| 上限 | **80** 人 |
| 列布局 | 每列 **20** 行；行高 **9**（行背景填 `y..y+8`）；列间距 **5**；顶部 `y=10`；整体水平居中 |
| 列宽 | `min(cols*(头像+最长名+分数+13), 屏宽-50) / cols` |
| 行背景 | `options.getBackgroundColor(553648127)`，默认 **0x20FFFFFF** |
| 延迟条 | `<0` 未知；`<150` 五格；`<300` 四格；`<600` 三格；`<1000` 两格；否则一格；图标 10×8，画在 `xo + slotWidth - 11` |

已实现：排序（三级，队伍待补）、80 上限**取最优八十**而非到达顺序、列换行与居中、延迟阈值（参数化断言 11 个边界）、包分发（`player_info_update`=71 / `player_info_remove`=70，ID 取自原版注册表 dump 并已用 9 个既有包 ID 反向校验）、行绘制（背景 0x20FFFFFF + 名字 + 五格延迟条，与界面同一批次）。

### 8.4 聊天（2026-10-29）

**线格式**（包 ID 取自原版注册表 dump，与既有 9 个 ID 一并校验）

| 方向 | 包 | ID | 负载 |
| --- | --- | --- | --- |
| 客户端→服务端 | `chat` | 9 | 文本(≤256) + 时间戳(long) + 盐(long) + **有符号?**(bool) + 已读偏移(VarInt) + **固定 20 位** bitset(3 字节) + 校验和(byte) |
| 客户端→服务端 | `chat_command` | 7 | 仅命令文本（**保留前导 `/`**）|
| 服务端→客户端 | `system_chat` | 124 | 待接（NBT 组件 + 是否覆盖聊天栏）|
| 服务端→客户端 | `player_chat` | 66 | 待接（含签名/会话校验）|
| 服务端→客户端 | `disguised_chat` | 33 / `delete_chat` 31 | 待接 |

无聊天会话时，签名位发 **false**、已读偏移 0、20 位全 0、校验和 0（原版把 0 视为"忽略"）。
这些字段**照发零值而不是省略**——省略会让整包结构不成立。

**提示框样式**（对齐原版 `ChatScreen`）

| 项 | 数值 |

| 文本起点 | `(4, h-13)`，8 px 字高 |
| 上限 | 256 字符 |
| `/` 键 | 打开时**自带 `/`**，可直接接命令 |
| 打开时 | 释放鼠标捕获；**移动与视角不累积**（原版把键盘交给屏幕）|
| 提交 | `/` 开头走 `chat_command`，否则 `chat`；空行不发送 |

## 9. 2D 渲染契约

- 独立于世界渲染的管线：正交投影、关闭深度测试、开启 alpha 混合、`scissor` 裁剪
- 顶点格式专用且紧凑（位置 2 + UV 2 + 颜色 4，约 20 字节），**不复用** 3D 的 48 字节布局
- 坐标以**虚拟分辨率**表达，按 GUI 缩放映射到像素；缩放采用浮点并对齐到像素网格，避免整数取整错位
- 形状（纯色矩形、边框）与纹理、文字共用同一批次，按材质分段提交
- 顶点与索引缓冲常驻并按需增长（沿用世界几何所用的"常驻 + 原地改写"策略，见 `docs/specs/network/play-movement.md` §7.25）

## 10. 性能预算与测量

数值写入 `docs/specs/quality-attributes.md` 并纳入门禁；此处只列指标与判定口径。

| 指标 | 阈值 | 测量方法 |
| --- | --- | --- |
| UI 每帧 CPU（聊天 + 玩家列表） | ≤ 0.3 ms | 窗口日志 `ui:` 分段计时 |
| UI 每帧 CPU（36 槽容器） | ≤ 1.0 ms | 同上 |
| 稳态分配 | **0 字节 / 帧** | `GC.GetAllocatedBytesForCurrentThread` 前后差（原则 3.6） |
| 绘制提交次数 | ≤ 3 次 / 屏幕 | `UiMetrics` |
| 四边形数（20 人玩家列表） | ≤ 200 | `UiMetrics` |
| 布局重算 | 空闲帧 **0** 次、每帧 ≤ 1 次 | 计数器 |
| 字形缓存命中率 | ≥ 99% | 计数器 |
| 热加载 | 渲染线程解析次数 **= 0** | 线程断言 + 耗时统计 |
| 常驻内存（树 + 字形图集） | ≤ 8 MB | 运行后报告 |

失败判定：任一阈值被超出即视为回归，需在提交内修复或记录受控偏差（原则 9）。

## 11. 防扩散规则

1. **YAGNI 门禁**：新增控件类型必须已有真实屏幕在使用，否则不予合并
2. **单一绘制出口**：只有 batcher 接触批次；控件只追加数据
3. **布局单趟**：不引入通用约束求解器；三种容器不够时，改用**纯代码屏幕**而不是扩引擎
4. **纯代码逃生舱**：任何屏幕允许完全用代码实现（容器 / 合成先走这条），声明式只覆盖稳定的部分
5. **架构门禁进 CI**：`Client.Ui` 不得引用 WGPU 类型或启动器；`Framework` 不得引用控件；模组契约不得引用内部类型
6. **热路径标注**：所有每帧路径标 `[HotPath]` 并配零分配测试

## 14. 风险与未决项

| 风险 | 缓解 |
| --- | --- |
| 布局引擎越写越大 | 固定单趟 + 仅三种容器；不足即改纯代码屏幕 |
| 文本测量每帧重算 | 行布局缓存 + 脏标记 |
| CJK 宽度与断行 | 位图字体宽度表；先单行截断，换行后续补 |
| 热加载丢状态 | 按 `id` 迁移；不可迁移时只丢该控件 |
| 声明式表达力不足 | 纯代码逃生舱，不硬撑扩展格式 |
| 与原版像素级偏差 | 布局数值取自原版可观测布局，用矩形断言守护 |

未决项：

- 标记扩展的扩展边界（`{Binding}` 之外还要不要 `{x:Reference}` / `{TemplateBinding}`）待 P2 决定
- 手柄与触摸支持后置（首批只做键鼠）；键盘导航（Tab/方向键）在 P2 补
- 是否引入可滚动的富文本（聊天分行、颜色、点击事件）细节待 P1
- **模组契约的具体形状未定**（所有者 2026-10-29：暂不确定）。倾向方向：只经公开界面接口注册控件与屏幕，
  不暴露内部类型；定稿前不得在模组侧引入界面 API
