# jar 分析文档的组织方式

本目录存放对 Minecraft 26.3 jar 的**行为级**分析结果。分析的目的是回答"这个子系统做什么、边界在哪、对应到 C# 的哪个模块"，不是复述实现。

## 组织原则

- 第一层按**子系统**分目录，第二层按**主题**分文件。禁止"一个大文件装下整个子系统"。
- 一个文件一个主题；文件之间只通过链接关联，不复制内容造成双份真相。
- 每个子系统目录必须有 `README.md`：该子系统的职责概述、文件清单、已完成/未完成的分析项。
- 子系统目录的命名应尽量对齐最终 C# 模块名，减少后续翻译成本。

## 建议的第一层划分（随分析进展修正）

```
analysis/
  README.md              本文件：组织方式 + 总进度
  <子系统>/
    README.md            子系统概述与文件清单
    <主题>.md            单主题分析，如 registry.md / tick-loop.md
```

## 每份分析文档必须交代

1. **职责**：这个子系统/结构在整体里承担什么。
2. **边界依据**：为什么它属于 Client / Server / Common / 外围宿主层。
3. **对 C# 的映射**：打算落到哪个模块，或分成哪几个模块。
4. **可观测行为**：输入到输出的行为规格（数值、时序、状态转移）。
5. **性能特征**：已知开销集中点，是否值得优化（作为 `benchmarks/` 的输入）。
6. **证据指针**：外部工作区的分析运行编号与小节定位。

## 合规约束

- 不粘贴反编译源码、字节码、原始实现片段。
- 不记录可直接还原实现的大段签名清单；需要记录接口形态时，用行为描述 + 最小必要签名。
- 分析产生的工作区（反编译输出、解包内容）位于**仓库之外**，本目录只放结论与指针。
